## Stage 1 — Architecture

**Goal**: Understand Python's role in infrastructure automation — how scripts interact with remote systems and APIs, and how to structure reusable code that others can maintain.

**Read in this order**:

- [How It Works](../architecture/how-it-works/) — CPython interpreter model, the GIL, virtual environment isolation, `pip` dependency resolution, and the standard library (subprocess, os, pathlib, logging, argparse)
- [Design Standards](../architecture/design-standards/) — project layout (`src/` layout vs flat), virtual environment conventions, `requirements.txt` vs `pyproject.toml`, structured logging patterns, and CLI entry points via `argparse` or `click`
- [Integrations](../architecture/integrations/) — `paramiko` for SSH automation, `requests` for REST API calls, `pyVmomi` for vSphere, `netmiko` for network device CLI, and `boto3`/`azure-mgmt` for cloud providers

**Key concepts before moving on**:

- Always use a virtual environment — global `pip install` will cause version conflicts across projects on shared servers
- `requests` raises exceptions only on network errors; HTTP 4xx/5xx responses must be checked with `response.raise_for_status()`
- `paramiko` requires explicit host key verification — disable it only in fully trusted, air-gapped lab environments
- Log at `DEBUG` level for diagnostic details, `INFO` for normal operations, and `ERROR` for failures — never use `print()` in production scripts

**Why first**: Infrastructure Python scripts run against production systems. A consistent project structure and dependency management strategy prevents environment drift and makes scripts maintainable by others.

## Stage 2 — Deployment

**Goal**: Package and deploy Python automation so it runs reliably in CI pipelines, scheduled jobs, and operator workstations.

**Read**:

- [Deploy](../deploy/) — virtual environment creation and activation, `pip install -r requirements.txt`, script packaging with `setuptools`, and distribution to shared execution environments (CI runner, cron server, AWX EE)
- [Install & Upgrade](../operations/install-upgrade/) — Python version management with `pyenv`, `pip-audit` for vulnerability scanning, library upgrades and compatibility testing, and `pip-compile` for deterministic lock files

**Deployment principles**:

- Pin all dependencies in a lock file (`requirements.txt` generated by `pip-compile`) to ensure reproducible installs
- Test scripts against the same Python version that runs in production — use `pyenv` to manage multiple versions locally
- Run `bandit -r src/` in CI to catch common security issues before scripts reach production

## Stage 3 — Operations

**Goal**: Run, monitor, and maintain Python automation scripts in production without silent failures or undetected errors.

**Read in this order**:

- [Health Checks](../operations/health-checks/) — run the routine first on every shift; scheduled script exit codes (non-zero = failure), log output review for ERROR/WARNING entries, and API endpoint connectivity checks
- [CLI Reference](../operations/cli-reference/) — `python`, `pip`, `pip-compile`, `venv`, `pytest`, `pylint`/`ruff`, `bandit`, `black` command patterns for daily development and maintenance
- [Procedures](../operations/procedures/) — adding a new library (add to `requirements.in`, run `pip-compile`, test), updating a script for API breaking changes, and rotating credentials used by automation scripts
- [Backup & Restore](../operations/backup-restore/) — script repository backup (Git remote), virtual environment recreation from lock file, and API credential backup in a secret store
- [Scripts](../operations/scripts/) — reusable helper modules: bulk SSH command runner via `paramiko`, vSphere inventory export via `pyVmomi`, REST API polling template with retry/backoff, and Jinja2 config templating

**Daily rhythm**: Review overnight job logs → check exit codes → validate API credential expiry dates → run `pip-audit` weekly.

## Stage 4 — Security

**Goal**: Prevent credentials from appearing in code or logs, and ensure scripts fail safely on unexpected conditions.

**Read**:

- [Access Control](../security/access-control/) — service account scoping for automation (least-privilege API tokens), per-script credential isolation, and audit logging for all privileged API calls made by scripts
- [Authentication](../security/authentication/) — reading credentials from environment variables or secret stores (Vault, AWS Secrets Manager), avoiding hardcoded passwords, SSH key-only authentication with `paramiko`, and token rotation automation
- [Encryption](../security/encryption/) — enforcing TLS verification in `requests` (`verify=True` always), encrypted secret storage, `cryptography` library for any in-script encryption, and secure random generation with `secrets` module
- [Hardening](../security/hardening/) — input validation with `argparse` types, exception handling that logs and exits cleanly rather than swallowing errors, `bandit` static analysis in CI, and `pip-audit` for dependency vulnerability scanning

---

## Stage 5 — Troubleshooting

**Goal**: Diagnose script failures, API errors, and environment issues without destructive re-runs against production systems.

**Read**:

- [Common Issues](../troubleshooting/common-issues/) — `ModuleNotFoundError` (wrong venv activated), SSL certificate verification failure, SSH `AuthenticationException`, `pyVmomi` API version mismatch after vCenter upgrade, and `requests.exceptions.Timeout`
- [Diagnostics](../troubleshooting/diagnostics/) — structured `logging` DEBUG output, `pdb.set_trace()` breakpoints for interactive debugging, full `traceback` analysis, and `requests` session hooks for HTTP request/response logging
- [Escalation](../troubleshooting/escalation/) — library GitHub issues (check closed issues first), PyPI package maintainer contact for security vulnerabilities, and vendor API support for `pyVmomi`/`netmiko` unexpected behaviour

**Why last**: Troubleshooting makes most sense once you understand the script's dependencies, the target API contract, and what a successful run produces end to end.
